Container at War: Why «Distroless» is Not Enough and How to Defend Your Workloads

A minimal container image strips away the shell and standard utilities. But when an application has an execution flaw, the runtime interpreter itself becomes the weapon.

1. The False Sense of Security in Minimal Images

In recent years, cloud-native best practices have settled on a standard recommendation: «Use Distroless or minimal Alpine bases, remove /bin/sh, delete curl and wget, and you are protected.»

While minimal images provide clean hygiene and reduce common vulnerability scanners' noise, they address installation surface rather than execution surface. When an application written in Node.js or Go suffers from a Local File Inclusion (LFI) flaw or an arbitrary memory execution path, an attacker does not need an external bash binary. They can operate straight within the process space: 

// Reading sensitive files in memory, even inside a shell-less container
const fs = require('fs');
const token = fs.readFileSync('/var/run/secrets/kubernetes.io/serviceaccount/token', 'utf8');
process.stdout.write(token);

2. The Live Arena at Come To Code 2026

During the keynote at Come To Code 2026, we demonstrated this reality across two parallel environments: a local Docker daemon and a real Google Kubernetes Engine (GKE) cluster.

In the unhardened round, an LFI vulnerability allowed the attacker to reach the mounted Kubernetes service account token, inspect network interfaces, and invoke arbitrary system calls.

In the second round, kernel security controls were activated: AppArmor LSM to enforce strict path confinement and deny sensitive file access, and Seccomp-BPF filters to restrict allowed syscalls to an application-specific allowlist.

«An attacker cannot execute what the kernel categorically refuses to dispatch.»

3. Practical Hardening: Bridging Applications and Infrastructure

Security is a chain, and the weakest link determines the outcome. As my colleague Matteo Madeddu highlighted in his reference on Docker security and Linux capabilities, container defense requires host-level awareness and disciplined profile management.

Key takeaways for production container defense:

  • Automated Syscall Profiling: Using tools like our skill-seccomp-apparmor-profiler to trace legitimate process execution in staging environments, drafting allowlists with deterministic verification.
  • Least Privilege by Default: Dropping all unnecessary Linux capabilities (--cap-drop=ALL) and strictly forbidding privilege escalation (allowPrivilegeEscalation: false).
  • Host and Node Baseline: Ensuring nodes (whether EC2, Bottlerocket, or GKE) enforce CIS benchmarks and enforce IMDSv2 to prevent cloud credential exfiltration.
