Container at War: Beyond the «Distroless» Myth

«More secure» does not mean «secure.» Stripping away /bin/sh and package managers shrinks your installation surface, not your execution surface. When your application has a bug, the runtime interpreter itself is the weapon.

Let me get one thing out of the way first: I work in security at RedCarbon, but at heart I am still a software developer. I write JavaScript, TypeScript, Go, and occasionally Python—which mostly means I know how to introduce bugs in four different ecosystems.

Every time container security comes up in an architecture review, the same comforting mantras surface within five minutes: «We use Distroless images, there is no shell inside», «We run on a managed GKE cluster», or «We enabled the default Seccomp profile.» The fastest way to get hurt in security is to say: «I used tool X, so I'm done.» The moment we think like that, we have stopped reasoning.

At Come To Code 2026 in Pignola, right after my friend Davide Imola showed how to catch vulnerabilities in source code with Argus, I took the stage to show the opposite side of the coin: what happens when a bug slips through into production. I stepped outside my pure-developer comfort zone—into the world of kernel LSMs, syscall filters, and DevOps headaches at 2 AM reading apparmor_parser man pages—and pitted five containers against live attacks on Docker and Google Kubernetes Engine (GKE).

«The weakest link in a security chain defines the security of the entire system.» Doesn't matter how thick the other links are—what matters is where the chain snaps.

0. The Arena: 5 Containers, Only 3 Images

Before firing a single request, let us look at the architecture of the lab (github.com/gafreax/container-at-war). There are five running services on ports 6661 through 6665, but the build pipeline produces only three container images:

  • Image 1 — Classic Node (1.16 GB): Standard full Debian-based Node.js image with /bin/sh, coreutils, package managers, running as root (app-classic on port 6661).
  • Image 2 — Distroless Node (162 MB): Built via multi-stage Dockerfile on top of gcr.io/distroless/nodejs22-debian12. No shell, no curl, no ls, no package manager. This single image powers both app-distroless (port 6662) and app-distroless-hardened (port 6663).
  • Image 3 — Distroless Static Go (8.22 MB): A static Go binary (CGO_ENABLED=0) inside gcr.io/distroless/static-debian12. Literally nothing in the filesystem except the binary itself. This single image powers both app-go-distroless (port 6664) and app-go-distroless-hardened (port 6665).

Why three images for five services? Because container hardening is a runtime property, not an image property. A container does not have its own kernel; it shares the host node's Linux kernel. Linux Security Modules (AppArmor) and syscall filters (Seccomp-BPF) do not live inside your Dockerfile—they are enforced by the host kernel via security_opt in Docker Compose or securityContext in Kubernetes.

Act I — The False Victory: Command Injection vs. Distroless

We start with a classic flaw in our Fastify application: unsanitized user input passed straight to child_process.exec(): 

// 1. Classic Command Injection (via exec -> requires /bin/sh)
fastify.get('/attack/command-injection', (request, reply) => {
    const ip = request.query.ip || '8.8.8.8';
    exec(`ping -c 1 ${ip}`, (error, stdout, stderr) => {
        if (error) {
            return reply.code(500).send(`[FAILED] ${error.message}\n`);
        }
        return reply.send(stdout);
    });
});

Against app-classic (port 6661), passing ?ip=8.8.8.8;id executes immediately as uid=0(root). When we fire the exact same payload at app-distroless (port 6662), the attack dies with HTTP 500: 

[FAILED] spawn /bin/sh ENOENT

Under the hood, Node's child_process.exec() does not invoke ping directly—it calls /bin/sh -c "ping -c 1 ...". Because the distroless image never copied a shell into the rootfs during the multi-stage build, execve("/bin/sh", ...) returns ENOENT (Error NO ENTry).

Distroless 1, Attacker 0. End of the talk? Not quite. I cheated: I picked the one attack vector that explicitly depends on /bin/sh.

Act II — The Illusion Collapses: LFI, Kubernetes Tokens & Shell-less RCE

What happens when the vulnerability does not ask the OS to spawn an external binary, but instead uses the legitimate APIs of the language runtime? Look at the next two endpoints in the exact same Distroless container: 

// 2. LFI / Path Traversal (pure Node fs API -> no shell needed)
fastify.get('/attack/path-traversal', async (request, reply) => {
    try {
        return reply.send(fs.readFileSync(request.query.file, 'utf8'));
    } catch (err) {
        return reply.code(500).send(`Read error: ${err.code || err.message}\n`);
    }
});

// 3. True RCE (arbitrary JS execution via eval -> the interpreter IS the shell)
fastify.get('/attack/eval-rce', (request, reply) => {
    try {
        const result = eval(request.query.code);
        return reply.send(`RCE result: ${result}\n`);
    } catch (err) {
        return reply.code(500).send(`RCE error: ${err.message}\n`);
    }
});

When we hit /attack/path-traversal on app-distroless, the absence of /bin/sh or cat is completely irrelevant. Node's fs.readFileSync() issues an openat(2) and read(2) syscall directly from the Node process:

  • Requesting ?file=/etc/passwd dumps the user database immediately (complete with our stage easter-egg user darth_vader running /bin/force_choke).
  • Requesting ?file=/var/run/secrets/come-to-code-supersecure-token dumps our "supersecure" file—which turns out to be an ASCII-art banner where the word "supersecure" in the filename was the only security control.
  • Worse, in a Kubernetes pod, every container has a ServiceAccount credential mounted by default at a well-known path. Requesting ?file=/var/run/secrets/kubernetes.io/serviceaccount/token exfiltrates the cluster JWT token cleanly. From there, an attacker does not care about your container anymore—they talk directly to the Kubernetes API server for lateral movement across the cluster.

And what about /attack/eval-rce? The obsession with removing /bin/sh assumes an attacker wants a POSIX shell. If your workload runs an interpreter (Node.js, Python, Ruby, PHP), the runtime interpreter is already a shell. Passing require('fs').readFileSync('/var/run/secrets/kubernetes.io/serviceaccount/token','utf8')—or opening a reverse TCP socket via Node's native net module—gives full Remote Code Execution without ever spawning a child process.

In terms of the 4C model of Cloud Native Security (Code → Container → Cluster → Cloud), LFI and eval live in the innermost ring (Code), while Distroless only trims the second ring (Container). Shrinking the image from 1.16 GB to 162 MB reduced our installation surface, not our execution surface.

Act III — Kernel Boundaries: AppArmor & the Blacklist Trap

If the application code is compromised and attempts to read sensitive paths like /var/run/secrets/kubernetes.io/serviceaccount/token, who has the authority to stop the openat(2) call? Only the Linux kernel on the host node.

On app-distroless-hardened (port 6663), we run the exact same Distroless image, but we instruct the runtime to drop root, mount the root filesystem read-only, and attach an AppArmor LSM profile: 

# docker-compose.yml (app-distroless-hardened)
read_only: true
user: "1000"
security_opt:
  - apparmor=docker-node-hardened

First, a critical observation: neither read_only: true nor user: "1000" stops our LFI attack. Why? Because LFI is a read operation, and the Kubernetes ServiceAccount token has to be readable by the user running the Node process if the application ever talks to the cluster API.

What actually stops the token theft on port 6663 is our AppArmor profile loaded into the host kernel: 

#include <tunables/global>

profile docker-node-hardened flags=(attach_disconnected,mediate_deleted) {
  #include <abstractions/base>
  #include <abstractions/nameservice>

  network,
  file,

  # Explicitly deny sensitive paths (Blacklist approach for stage demo)
  deny /etc/passwd mrw,
  deny /etc/shadow mrw,
  deny /var/run/secrets/kubernetes.io/serviceaccount/** mrw,

  deny mount,
  deny ptrace,
}

Now, when app-distroless-hardened tries to read /etc/passwd or the Kubernetes ServiceAccount token via fs.readFileSync(), the kernel intercepts the file access and returns EACCES (Permission denied). Both attacks turn green (🟢 Blocked).

The Hole in the Blacklist

Look closely at the AppArmor profile above: it uses a denylist (blacklist)—allowing file, globally and blocking specific paths with deny. On stage, we then fire a third LFI request against the hardened container: 

curl "http://localhost:6663/attack/path-traversal?file=/etc/come-to-code.conf"

And out comes the secret configuration file (🔴 Succeeded). Why? Because whoever wrote the denylist remembered /etc/passwd and /var/run/secrets/kubernetes.io/serviceaccount/**, but forgot that a custom /etc/come-to-code.conf was mounted into the container.

A denylist only protects what you remember to forbid. The defender has to remember everything; the attacker only has to find one path you forgot. In production, AppArmor profiles must be built as default-deny allowlists: deny all file access by default, and explicitly allow only the application bundle (e.g., /app/** r,), runtime libraries, and required pseudo-filesystems.

Act IV — Phase Shift: Fileless Execution in Go (memfd_create) & Seccomp-BPF

At this point someone always asks: «Okay, Node.js has an interpreter and needs lots of files. What if I compile a static Go binary with CGO_ENABLED=0 and put it in distroless/static? It's 8 megabytes, no libc, no shell, no interpreter, read-only filesystem, and AppArmor locked down!»

Enter app-go-distroless (port 6664). Here we shift our threat model from initial access to post-exploitation and defense evasion—specifically MITRE ATT&CK T1620 (Reflective Code Loading). Suppose an attacker achieves code execution inside a compiled service (for instance via a compromised supply-chain dependency—think xz / CVE-2024-3094—or a memory corruption / deserialization flaw) and wants to drop and execute a second-stage ELF binary.

Writing to disk fails because readOnlyRootFilesystem: true is enabled, and AppArmor watches every path on the filesystem. So the attacker does not touch the disk at all. They invoke the Linux syscall memfd_create(2): 

func filelessHandler(w http.ResponseWriter, r *http.Request) {
	// Creates an anonymous file that lives strictly in RAM
	fd, err := unix.MemfdCreate("demo-in-ram", unix.MFD_CLOEXEC)
	if err != nil {
		w.WriteHeader(http.StatusInternalServerError)
		fmt.Fprintf(w, "[BLOCKED] memfd_create denied: %v\n", err)
		return
	}
	defer unix.Close(fd)

	// Write payload into the in-RAM file descriptor
	_, _ = unix.Write(fd, []byte("hello from RAM\n"))

	// Accessible via /proc/self/fd/N -> a real attacker calls execve() on this path
	memPath := fmt.Sprintf("/proc/self/fd/%d", fd)
	fmt.Fprintf(w, "[SUCCEEDED] fileless primitive available: in-RAM fd %d at %s\n", fd, memPath)
}

On app-go-distroless, this succeeds immediately:

  • Distroless static image? Useless—memfd_create is a kernel syscall (#319 on x86_64), not a binary on disk.
  • Read-only root filesystem? Useless—nothing is written to disk; the anonymous file resides in RAM.
  • AppArmor? Blind to the creation of the anonymous file descriptor, because AppArmor mediates file paths, not raw syscalls.

To stop a syscall primitive, you must defend at the syscall layer with Seccomp-BPF. In app-go-distroless-hardened (port 6665), we attach a Seccomp profile that intercepts memfd_create and memfd_secret at the kernel boundary and returns EPERM (errnoRet: 1): 

{
  "defaultAction": "SCMP_ACT_ALLOW",
  "architectures": ["SCMP_ARCH_X86_64", "SCMP_ARCH_AARCH64"],
  "syscalls": [
    {
      "names": ["memfd_create", "memfd_secret"],
      "action": "SCMP_ACT_ERRNO",
      "errnoRet": 1,
      "comment": "Deny the fileless in-RAM execution primitive"
    }
  ]
}

When we hit port 6665, the kernel refuses to dispatch the syscall and the handler returns [BLOCKED] memfd_create denied: operation not permitted (🟢).

A classic trap to avoid: when people first write a Seccomp profile against fileless execution, they are tempted to block execve. Never block execve in your container's initial Seccomp profile—the container runtime (runc / crun) needs execve to launch your entrypoint process in the first place! Blocking it prevents the container from ever starting (exec ...: operation not permitted). And just like AppArmor, while a small denylist is great for teaching on stage, production Seccomp profiles should use a default-deny allowlist ("defaultAction": "SCMP_ACT_ERRNO") allowing only the exact syscalls your binary needs.

The «Managed Kubernetes» Myth: Live Verification on GKE

What if you deploy that exact Go service to a managed Kubernetes cluster like Google Kubernetes Engine (GKE) and enable Kubernetes' built-in default Seccomp profile (securityContext.seccompProfile.type: RuntimeDefault)?

We tested this live against a real GKE 1.35 cluster. The result surprises many engineers: with RuntimeDefault enabled, /attack/fileless-rce still returns HTTP 200 [SUCCEEDED]. Why? Because containerd's RuntimeDefault profile is designed for broad compatibility across arbitrary workloads, and memfd_create is permitted by default!

The lesson is brutal: «I have Seccomp enabled» does not mean «I have Seccomp protecting me against this threat.» To block memfd_create on Kubernetes, you need a custom Localhost Seccomp profile deployed to your nodes—or a stronger isolation boundary like GKE Sandbox (gVisor), which intercepts syscalls in a user-space sentry kernel. Managed Kubernetes operates on a shared responsibility model: the cloud provider patches the control plane and node OS, but they do not write your application code or your workload-specific syscall allowlists.

Act V — The Final Scoreboard & Why Shift-Left Is Non-Negotiable

Let us look at the complete scoreboard across all five containers at the end of the live demo:

Service (Port) Cmd Injection LFI /etc/passwd LFI K8s Token LFI .conf (Hole) JS eval() RCE Go memfd_create
app-classic (:6661) 🔴 Pwned 🔴 Pwned 🔴 Pwned 🔴 Pwned 🔴 Pwned —
app-distroless (:6662) 🟢 ENOENT 🔴 Pwned 🔴 Pwned 🔴 Pwned 🔴 Pwned —
app-distroless-hardened (:6663) 🟢 ENOENT 🟢 EACCES 🟢 EACCES 🔴 Bypass 🔴 Pwned —
app-go-distroless (:6664) — — — — — 🔴 RAM FD OK
app-go-distroless-hardened (:6665) — — — — — 🟢 EPERM

Notice that column five—eval() RCE—stays red (🔴) across every single runtime configuration.

Why didn't Distroless, non-root, read-only rootfs, AppArmor, or Seccomp stop eval()? Because eval() executes inside the legitimate interpreter process and uses the exact same syscalls (read, write, openat) and application files that your business logic needs to function. If you blocked those syscalls or files in the kernel, your application wouldn't run at all.

A bug in the Code ring can only be fixed in the Code ring. Runtime hardening contains the blast radius (stopping the attacker from reading /var/run/secrets/... or calling memfd_create after they get in), but eliminating eval(), path traversal, and hardcoded secrets requires Shift-Left security before the image is ever built:

  • Deterministic Static Analysis & Scanners: Integrating Semgrep, CodeQL, gosec, Bandit, Gitleaks, and OSV-Scanner into CI/CD pipelines.
  • AI-Assisted Security Review with Human-in-the-Loop: Years ago, writing an AppArmor or Seccomp profile meant spending hours in kernel documentation—or copying a 2013 Stack Overflow answer with three upvotes and praying your pod would still boot. Today, AI can draft a profile from observed behavior (skill-seccomp-apparmor-profiler) and orchestrate code triage (like Argus, presented by Davide Imola). But a broken security profile stated with LLM confidence is worse than having no profile at all: it gives you a false sense of security. If «more secure» does not mean «secure», «more automated» does not mean «correct» without human verification and mandatory negative tests.
  • Host & Capabilities Hygiene: As my colleague Matteo Madeddu thoroughly documented in his guide on Docker security and Linux capabilities, always pair LSM/Seccomp profiles with --cap-drop=ALL and allowPrivilegeEscalation: false.

Distroless is one link in the chain. AppArmor is one link. Seccomp is one link. Managed Kubernetes is one link. None of them, alone, is «security.» The next time you read «secure by default» on a slide or a vendor page, ask yourself one question: «Secure against what?»

(And no, I don't spend all my weekends writing AppArmor rules—when I just want to enjoy the terminal as a developer, I build small CLI tools like gotrova. No penguins were harmed in the making of this research. Many AI agents were.)
