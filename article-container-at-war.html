Container at War: Beyond the «Distroless» Myth

«More secure» does not mean «secure.» Adopting a tool because it is the industry buzzword of the moment is not a threat model. A practical escalation through Docker runtime primitives, AppArmor, SELinux, and Seccomp-BPF.

Lab Repo: github.com/gafreax/container-at-war ↗ GitHub @gafreax ↗

In software engineering and container security, the fastest way to leave a production system exposed is to fall in love with a buzzword. Whenever a defensive technology becomes the standard recommendation of the moment—whether it is Distroless images, managed Kubernetes, or default Seccomp profiles—it is dangerously easy to treat its adoption as the finish line: «We switched to tool X, therefore we are secure.»

The moment we reason like that, we have stopped engineering. Tools and Docker flags are not magic shields; each control mitigates one specific class of threat at one specific boundary. Security is not a checkbox you tick by swapping a base line in a Dockerfile—it is an engineering escalation governed by a fundamental rule:

«The weakest link in a security chain defines the security of the entire system.» It does not matter how strong the other links are; what matters is where the chain snaps.

To verify empirically what each layer of the Docker and Linux kernel stack actually stops—and what it silently lets through—I built an open-source lab on my GitHub: github.com/gafreax/container-at-war.

In this article, we will walk through a progressive hardening escalation across five containers built from three images: starting from image build-time hygiene (Distroless), escalating to Docker runtime flags (User Namespaces, Capabilities, Cgroups, Read-Only rootfs), then to Kernel Mandatory Access Control (AppArmor and SELinux), down to Kernel Syscall Filtering (Seccomp-BPF), and finally to Shift-Left code analysis.

Level 0 — Image & Build-Time Hygiene: What «Distroless» Images Are and Why They Exist

Before attacking a Distroless container, we need to understand why Distroless images were created and what problem they genuinely solve.

Pioneered by Google, Distroless images contain only your application and its direct runtime dependencies (such as glibc, OpenSSL, CA certificates, and the language runtime like Node.js or Python). They deliberately strip out everything else you would find in a standard Linux distribution: there is no package manager (apt, apk, yum), no shell (/bin/sh, /bin/bash), and no standard system utilities (curl, wget, ps, ls, cat).

They are built via multi-stage Dockerfiles: you compile your code and install dependencies inside a full build stage, then copy only the compiled artifacts into the minimal Distroless runtime stage. The shell is not "deleted" in a later layer—it was never copied into the final root filesystem in the first place.

Adopting Distroless brings three major engineering benefits:

  • Drastically smaller footprint: In our lab (src/demo-node & src/demo-go), the standard Debian-based Node.js image weighs 1.16 GB, while the equivalent Distroless Node.js image is 162 MB, and the static Go Distroless image is just 8.22 MB.
  • Higher signal-to-noise ratio in CVE scanners: By eliminating hundreds of unused OS packages, your vulnerability scanner stops paging your team for CVEs in system binaries your application never invokes.
  • No "living-off-the-land" utilities or setuid binaries: In traditional Debian or Ubuntu images, attackers routinely abuse /bin/sh, curl, or lingering setuid/setgid binaries for privilege escalation—which otherwise must be manually located and "defanged" in your Dockerfile via find / -xdev -perm +6000 -type f -exec chmod a-s {} \;, as my colleague Matteo Madeddu demonstrates in his Docker security guide. In a Distroless image, those binaries simply do not exist on disk.

In docker-compose.yml, we spin up five services on ports 6661 through 6665 using only three images:

  • Image 1 — Classic Node (1.16 GB): Powers app-classic (:6661), running as root with a full Debian userland and shell.
  • Image 2 — Distroless Node (162 MB): Powers both app-distroless (:6662) and app-distroless-hardened (:6663).
  • Image 3 — Distroless Static Go (8.22 MB): Powers both app-go-distroless (:6664) and app-go-distroless-hardened (:6665).

Why three images for five services? Because container hardening is a runtime property, not an image property. A container does not have its own kernel; it shares the host node's Linux kernel. Let us see what happens when we attack them.

Act I — The Promise Confirmed: Command Injection on Classic vs. Distroless

Let us start where Distroless delivers on its exact promise. In src/demo-node/server.js, our first endpoint contains a classic Command Injection vulnerability where unsanitized user input is concatenated into child_process.exec(): 

// src/demo-node/server.js
// 1. Classic Command Injection (via exec -> requires /bin/sh)
fastify.get('/attack/command-injection', (request, reply) => {
    const ip = request.query.ip || '8.8.8.8';
    exec(`ping -c 1 ${ip}`, (error, stdout, stderr) => {
        if (error) {
            return reply.code(500).send(`[FAILED] ${error.message}\n`);
        }
        return reply.send(stdout);
    });
});

When we send the payload ?ip=8.8.8.8;id to app-classic (port 6661), the attack succeeds immediately (🔴). Under the hood, Node's child_process.exec() does not invoke ping directly; it spawns a shell to parse the command string: 

execve("/bin/sh", ["sh", "-c", "ping -c 1 8.8.8.8;id"], ...)

On a standard Docker image, /bin/sh, ping, and id are all present in the container filesystem. No error occurs: the shell runs ping, executes the injected id command, and returns uid=0(root) gid=0(root) to the caller.

Now we send the exact same payload to app-distroless (port 6662), which runs the identical Node.js code inside gcr.io/distroless/nodejs22-debian12. This time, the exploit fails immediately with HTTP 500 (🟢): 

[FAILED] spawn /bin/sh ENOENT

Because /bin/sh was never copied into the Distroless rootfs, the kernel's execve() syscall returns ENOENT (Error NO ENTry). The command injection is dead in the water.

If we stopped testing here, we would declare victory. In reality, we only tested an attack vector that explicitly depends on an external shell binary.

Act II — Dismantling the Illusion: Separating LFI from True RCE

What happens when an attacker stops asking the operating system for /bin/sh and instead leverages the native capabilities of our application runtime? In Act II, we test two distinct vulnerability classes against app-distroless (:6662). Both bypass Distroless effortlessly.

2.1 Local File Inclusion (LFI) & Kubernetes Token Exfiltration

The second endpoint in src/demo-node/server.js exposes a Path Traversal / Local File Inclusion flaw using Node's built-in fs module: 

// 2. LFI / Path Traversal (pure Node fs API -> no shell needed)
fastify.get('/attack/path-traversal', async (request, reply) => {
    try {
        return reply.send(fs.readFileSync(request.query.file, 'utf8'));
    } catch (err) {
        return reply.code(500).send(`Read error: ${err.code || err.message}\n`);
    }
});

When we request /attack/path-traversal?file=/etc/passwd on the Distroless container, the absence of /bin/sh or cat is irrelevant. fs.readFileSync() does not spawn a child process—it issues the Linux syscalls openat(2) and read(2) directly from the Node.js process and dumps /etc/passwd (🔴).

In a Kubernetes cluster, the impact escalates immediately. By default, Kubernetes mounts a ServiceAccount credential inside every pod at a well-known path. When the attacker requests: 

GET /attack/path-traversal?file=/var/run/secrets/kubernetes.io/serviceaccount/token

the Distroless container reads and returns the pod's JWT token (🔴). With that credential, the attacker pivots straight to the Kubernetes API server for lateral movement across the cluster.

2.2 True RCE: When the Runtime Interpreter Is the Shell

LFI gives arbitrary file reads, but what about full Remote Code Execution (RCE) inside a container that has no shell? Look at the third endpoint: 

// 3. True RCE (arbitrary JS execution via eval -> no shell needed)
fastify.get('/attack/eval-rce', (request, reply) => {
    try {
        const payload = request.query.code;
        const result = eval(payload);
        return reply.send(`RCE result: ${result}\n`);
    } catch (err) {
        return reply.code(500).send(`RCE error: ${err.message}\n`);
    }
});

The belief that stripping /bin/sh prevents RCE assumes an attacker needs a POSIX shell to run code. If your container runs an interpreted runtime—Node.js, Python, Ruby, PHP, or the JVM—the runtime interpreter is already a shell.

By passing JavaScript into eval() (or exploiting an unsafe deserialization, prototype pollution, or template injection sink), an attacker executes arbitrary code in memory within the Node process: reading files via require('fs'), exfiltrating data over HTTP, or opening raw network sockets via require('net') (🔴).

In the 4C model of Cloud Native Security (Code → Container → Cluster → Cloud), both LFI and RCE live in the innermost ring (Code), while Distroless only trims the second ring (Container). Shrinking the image from 1.16 GB to 162 MB reduced our installation surface, not our execution surface.

Act III — Escalation Level 1: Docker Runtime Primitives (Namespaces, Capabilities, Cgroups & Read-Only FS)

Once we realize that image minimalism does not stop application-level exploits, it is time to escalate our defenses to the Docker container runtime.

As my colleague Matteo Madeddu thoroughly documented in Security and Docker: tips and tricks, hardening a container starts with enforcing the Principle of Least Privilege across the core Linux primitives managed by Docker Engine (configured in docker-compose.yml for app-distroless-hardened): 

# docker-compose.yml (Escalation Level 1: Docker Runtime Flags)
app-distroless-hardened:
  read_only: true
  user: "1000"
  cap_drop:
    - ALL
  pids_limit: 100
  mem_limit: 256m
  security_opt:
    - no-new-privileges:true

Let us examine what each of these controls actually buys us at the kernel level:

  • User Namespaces & Unprivileged USER (user: "1000" + no-new-privileges): By default, unless User Namespace remapping is explicitly enabled on the Docker daemon, UIDs are shared between the container and the host: UID 0 (root) inside the container is UID 0 on the host kernel. Running as UID 1000 and enforcing no-new-privileges:true ensures the process cannot escalate privileges even if a binary carries a setuid bit.
  • Linux Capabilities (cap_drop: [ALL]): Since Linux kernel 2.2, the monolithic power of root is divided into granular per-thread units called capabilities (CAP_CHOWN, CAP_NET_RAW, CAP_MKNOD, CAP_SYS_ADMIN). Docker grants 14 capabilities by default; dropping all of them (--cap-drop=ALL) prevents a hijacked process from forging raw packets, changing file ownership, or manipulating kernel modules.
  • Read-Only Root Filesystem (read_only: true): Mounts the container's overlay filesystem as read-only, preventing an attacker from overwriting application code or dropping persistent backdoors onto disk.
  • Control Groups / Cgroups Governance (pids_limit, mem_limit, --cpus): By default, a container can consume unbounded host memory and spawn unlimited processes. Enforcing cgroup limits prevents a compromised container—or an eval() infinite loop—from launching a fork bomb or starving neighboring workloads on the node (Denial of Service).
  • Secret Hygiene: Never pass sensitive credentials as plain environment variables (-e SECRET=...), which are trivially exposed via docker inspect or by reading /proc/self/environ via LFI. Prefer short-lived, identity-bound credentials (such as Vault, GKE Workload Identity, or AWS IRSA).

The Escalation Verdict: These Docker runtime primitives are mandatory hygiene—they eliminate root breakouts, disk persistence, raw socket abuse, and fork-bomb DoS. Yet if we re-run our LFI and eval() attacks now, they still succeed (🔴)!

Why? Because LFI is a read operation (so read_only: true does nothing), /etc/passwd is world-readable, and the mounted Kubernetes ServiceAccount token must be readable by UID 1000 if the application ever communicates with the cluster API. To block unauthorized file reads inside the container, we must escalate one layer deeper: to Linux Security Modules (LSMs) in the host kernel.

Act IV — Escalation Level 2: Kernel Mandatory Access Control (AppArmor & SELinux)

When the Node.js process calls openat(2) on /var/run/secrets/kubernetes.io/serviceaccount/token, only a Mandatory Access Control (MAC) module inside the host Linux kernel can inspect the request and veto it before bytes are returned to user space.

Depending on your Linux distribution, the kernel enforces MAC through one of two LSMs: AppArmor (on Debian, Ubuntu, and GKE Container-Optimized OS) or SELinux (on RHEL, CentOS Stream, Fedora, OpenShift, and AWS Bottlerocket). Our lab repository provides working profiles for both in k8s/security/.

4.1 AppArmor (Path-Based LSM) & the Blacklist Trap

AppArmor mediates access by filesystem path (and capability). On app-distroless-hardened (port 6663), we load k8s/security/apparmor-node-profile into the host kernel with sudo apparmor_parser -r -W and attach it via security_opt: ["apparmor=docker-node-hardened"]: 

# k8s/security/apparmor-node-profile
#include <tunables/global>

profile docker-node-hardened flags=(attach_disconnected,mediate_deleted) {
  #include <abstractions/base>
  #include <abstractions/nameservice>

  network,
  file,

  # Denylist (blacklist) approach for demonstration:
  deny /etc/passwd mrw,
  deny /etc/shadow mrw,
  deny /var/run/secrets/kubernetes.io/serviceaccount/** mrw,

  deny mount,
  deny ptrace,
}

When we fire the LFI attack against port 6663 for /etc/passwd or /var/run/secrets/kubernetes.io/serviceaccount/token, the kernel intercepts openat(2) and denies it with EACCES (Permission denied, 🟢).

The Hole in the Blacklist: Look closely at how that teaching profile is structured—it grants global file, access and then uses deny rules for specific paths. When we request a custom configuration file mounted at /etc/come-to-code.conf: 

curl "http://localhost:6663/attack/path-traversal?file=/etc/come-to-code.conf"

the secret configuration is leaked immediately (🔴). Whoever wrote the denylist remembered standard OS files and the Kubernetes token path, but forgot the application's custom config file. A denylist only protects what you remember to forbid; in production, AppArmor profiles must be written as default-deny allowlists, permitting only /app/** r, and required runtime libraries.

4.2 SELinux (Label-Based LSM): Why Default container_t Fails and How to Fix It

What if your Docker or Kubernetes nodes run on Fedora, RHEL, or OpenShift with SELinux enabled in Enforcing mode?

Unlike AppArmor, SELinux is label-based (combining Type Enforcement with Multi-Category Security / MCS). By default, container runtimes launch containers under the process domain container_t with a unique random pair of MCS categories (e.g., s0:c123,c456), and label mounted container volumes (when using the :z or :Z volume flags, or Kubernetes projected volumes) as container_file_t with matching MCS categories.

Here is the catch: out-of-the-box SELinux does not stop our Act II LFI attack against the pod's own Kubernetes token. Why? Because default container-selinux is designed to isolate containers from the host OS (etc_t, usr_t) and from other containers (different MCS categories). Since the Kubernetes ServiceAccount token is mounted inside the pod for the pod's own use, it is labeled with the container's own container_file_t context! To default SELinux, fs.readFileSync() reading that token is a completely legal intra-container read.

To block intra-pod LFI with SELinux, we must write a custom SELinux CIL (Common Intermediate Language) policy module—provided in our lab at k8s/security/selinux-node-hardened.cil—that defines a confined process domain (docker_node_hardened.process) and a separate file type (docker_node_hardened.k8s_secret_t) for sensitive credentials: 

; k8s/security/selinux-node-hardened.cil
(block docker_node_hardened
    (blockinherit container)
    (blockinherit net_container)

    ; Dedicated SELinux type for sensitive mounted credentials
    (type k8s_secret_t)
    (roletype system_r k8s_secret_t)
    (typeattributeset file_type (k8s_secret_t))

    ; Allow the Node.js process to read only standard read-only app files
    (allow process container_ro_file_t (dir (getattr ioctl lock open read search)))
    (allow process container_ro_file_t (file (getattr ioctl lock map open read)))
    (allow process container_ro_file_t (lnk_file (getattr read)))

    ; Allow binding to TCP port 8080
    (allow process http_cache_port_t (tcp_socket (name_bind)))

    ; SELinux is default-deny: because there is NO (allow process k8s_secret_t ...)
    ; rule, any attempt to open/read a file labeled k8s_secret_t is denied (EACCES).
)

On an SELinux host, we load the policy module, label the sensitive token file with our restricted type, and pass label=type:docker_node_hardened.process to Docker: 

# 1. Load the custom CIL policy module (using udica base templates)
sudo semodule -i k8s/security/selinux-node-hardened.cil \
  /usr/share/udica/templates/{base_container.cil,net_container.cil}

# 2. Label the mounted secret with the restricted SELinux type
sudo chcon -t docker_node_hardened.k8s_secret_t ./k8s/mock-token

# 3. Run the container under the confined SELinux domain
docker run --rm -p 6663:8080 \
  --read-only --user 1000 --cap-drop=ALL \
  --security-opt no-new-privileges:true \
  --security-opt label=type:docker_node_hardened.process \
  -v ./k8s/mock-token:/var/run/secrets/kubernetes.io/serviceaccount/token:ro \
  app-distroless

Notice the architectural advantage of SELinux here: because SELinux is default-deny by construction, there is no "blacklist hole"—any file type not explicitly granted an (allow process ...) rule is automatically blocked by the kernel with an AVC denial (🟢).

Act V — Escalation Level 3: Fileless Execution in RAM (memfd_create) & Seccomp-BPF

At this stage, our filesystem is locked down: we have a minimal Distroless image, a read-only rootfs, dropped capabilities, and strict AppArmor/SELinux file confinement. What if we go even further and compile a static Go binary (CGO_ENABLED=0) inside gcr.io/distroless/static (8.22 MB total)?

Enter app-go-distroless (port 6664, source in src/demo-go/main.go). Here we shift to post-exploitation and defense evasion—specifically MITRE ATT&CK T1620 (Reflective Code Loading). Suppose an attacker achieves code execution inside the process (for example via a compromised supply-chain dependency or a memory corruption flaw) and wants to execute a second-stage ELF binary.

Because writing a binary to disk is blocked by read_only: true and watched by AppArmor/SELinux, the attacker never touches the disk. Instead, they invoke the Linux kernel syscall memfd_create(2): 

// src/demo-go/main.go
func filelessHandler(w http.ResponseWriter, r *http.Request) {
	// Creates an anonymous file that lives strictly in RAM
	fd, err := unix.MemfdCreate("demo-in-ram", unix.MFD_CLOEXEC)
	if err != nil {
		w.WriteHeader(http.StatusInternalServerError)
		fmt.Fprintf(w, "[BLOCKED] memfd_create denied: %v\n", err)
		return
	}
	defer unix.Close(fd)

	// Write ELF payload into the in-RAM file descriptor
	_, _ = unix.Write(fd, []byte("hello from RAM\n"))

	// Accessible via /proc/self/fd/N -> a real attacker calls execve() on this descriptor
	memPath := fmt.Sprintf("/proc/self/fd/%d", fd)
	fmt.Fprintf(w, "[SUCCEEDED] fileless primitive available: in-RAM fd %d at %s\n", fd, memPath)
}

Against app-go-distroless (:6664), this succeeds immediately (🔴):

  • Distroless static image? Irrelevant—memfd_create is a kernel syscall (#319 on x86_64), not a binary on disk.
  • Read-only rootfs & docker diff forensics? Irrelevant—no disk block is ever written. In standard incident response (as Matteo Madeddu highlights in his Docker forensics section), responders run docker diff to inspect files created or modified in a compromised container's overlay filesystem. Because memfd_create lives purely in RAM, docker diff shows zero changes on disk.
  • AppArmor / SELinux path & volume rules? Blind to the creation of the anonymous descriptor, because file-level LSM rules mediate filesystem paths/labels rather than raw syscall availability.

To stop a syscall primitive, we must escalate to the syscall boundary using Seccomp-BPF. On app-go-distroless-hardened (port 6665), we attach k8s/security/seccomp-go.json, which intercepts memfd_create and memfd_secret and returns EPERM (errnoRet: 1): 

// k8s/security/seccomp-go.json
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "architectures": ["SCMP_ARCH_X86_64", "SCMP_ARCH_AARCH64"],
  "syscalls": [
    {
      "names": ["memfd_create", "memfd_secret"],
      "action": "SCMP_ACT_ERRNO",
      "errnoRet": 1,
      "comment": "Deny the fileless in-RAM execution primitive"
    }
  ]
}

Now the kernel refuses to dispatch the syscall, returning [BLOCKED] memfd_create denied: operation not permitted (🟢).

The execve Trap & the GKE RuntimeDefault Myth:

  • Never block execve in your container's base Seccomp profile: The OCI runtime (runc / crun) needs execve to launch your entrypoint process! Blocking it prevents the container from starting at all.
  • Default Seccomp does NOT block memfd_create: Both Docker's default Seccomp profile and Kubernetes' securityContext.seccompProfile.type: RuntimeDefault (which we verified live on a Google Kubernetes Engine 1.35 cluster) block roughly 44 dangerous syscalls out of 300+ for general compatibility—leaving memfd_create wide open (HTTP 200 [SUCCEEDED]). Blocking it requires either a custom Localhost Seccomp profile (built as a default-deny allowlist) or a sandboxed runtime like GKE Sandbox (gVisor).

Look at column five: eval() RCE remains red (🔴) across every single runtime configuration.

Why couldn't Distroless, non-root, dropped capabilities, read-only rootfs, AppArmor, SELinux, or Seccomp stop eval()? Because eval() executes inside the legitimate interpreter process using the exact same syscalls (read, write, openat) and application files that normal business logic requires. Blocking those in the kernel would break the application itself.

A vulnerability in the Code ring can only be eliminated in the Code ring. Runtime hardening is essential to contain the blast radius after an exploit, but fixing code-level flaws requires Shift-Left engineering before docker build ever runs:

  • Deterministic Static Analysis & Scanners: Enforcing Semgrep, CodeQL, gosec, Bandit, Gitleaks, and OSV-Scanner in CI pipelines.
  • AI-Assisted Profiling & Triage with Human-in-the-Loop: Historically, auto-generating Seccomp profiles required dynamic probing tools like docker-slim (slimtoolkit) or manual strace sessions. Today we can pair behavioral tracing with AI skills like github.com/gafreax/skill-seccomp-apparmor-profiler to generate default-deny AppArmor/Seccomp allowlists from real staging execution, verified with mandatory negative tests, alongside code-review orchestrators like Argus. Because if «more secure» does not mean «secure», «more automated» does not mean «correct» without human verification.

Distroless is one link in the chain. Capabilities and Cgroups are one link. AppArmor and SELinux are one link. Seccomp is one link. None of them, in isolation, is «security.» The next time you read «secure by default», ask yourself: «Secure against what?»
