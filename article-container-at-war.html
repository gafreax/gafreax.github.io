Container at War: perché «distroless» non basta e come difendersi davvero

Un'immagine minimale toglie la shell e i binari di sistema all'attaccante. Ma quando il codice applicativo presenta una falla, l'interprete stesso diventa l'arma.

1. L'illusione della superficie ridotta

Negli ultimi anni, il mantra dell'industria cloud native è stato categorico: «usa immagini Distroless o Alpine, rimuovi /bin/sh, togli curl e wget, e sarai al sicuro».

È un ottimo primo passo di igiene, ma confonde la superficie di installazione con la superficie di esecuzione. Se un'applicazione Node.js o Go soffre di una vulnerabilità di tipo Local File Inclusion (LFI) o Remote Code Execution (RCE) tramite deserializzazione o prototype pollution, l'attaccante non ha bisogno di chiamare un binario bash esterno. Può eseguire codice direttamente nello spazio di memoria dell'interprete: 

// Esempio: lettura arbitraria della memoria o di file protetti
// anche all'interno di un container privo di shell
const fs = require('fs');
const secret = fs.readFileSync('/etc/passwd', 'utf8');
process.stdout.write(secret);

2. Il test sul campo a Come To Code 2026

Durante il talk a Pignola abbiamo allestito un'arena con due ambienti paralleli: un cluster GKE e un demone Docker locale, bersagliati in diretta da exploit mirati.

Nel primo round, l'applicazione compromessa girava su un container Node.js "distroless" non isolato. L'attacco ha esfiltrato file di configurazione, scansionato la rete interna del cluster e invocato chiamate di sistema arbitrarie.

Nel secondo round, abbiamo attivato la vera armatura: AppArmor per il confinamento dei file e delle capability, e Seccomp in modalità allowlist per bloccare alla radice le syscall non ammesse (come ptrace o tentativi di esecuzione di fileless shellcode in memoria).

«Non puoi invocare ciò che il kernel si rifiuta categoricamente di eseguire.»

3. Il tassello mancante: l'Hardening delle macchine (e l'approccio AWS)

In un talk di 45 minuti non c'è il tempo di coprire tutto. Come ha ben argomentato il collega Matteo Madeddu nel suo riferimento su docker-security (capabilities e least privilege), l'isolamento dei container non può prescindere dall'hardening del nodo host e dai profili delle immagini.

Ed è proprio qui che si proietta il prossimo talk per l'AWS User Group di Cuneo:

  • Meno live exploitation e più pragmatismo operativo: come sfornare template di nodi EC2 ed EKS (es. con Bottlerocket OS) già pronti con configurazioni di hardening conformi ai benchmark CIS.
  • Automazione dei profili Seccomp/AppArmor: come catturare i trace in staging con tool come il nostro skill-seccomp-apparmor-profiler e distribuirli sui nodi tramite Kubernetes Security Profiles Operator (SPO) o daemon set.
  • Integrazione nativa con AWS: gestione dell'identity con IAM Roles for Service Accounts (IRSA / EKS Pod Identity) evitando l'esposizione dei metadati dell'istanza (IMDSv2 obbligatorio).
